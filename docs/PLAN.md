# 台风实况网站产品与开发计划书

版本：0.1

日期：2026-11-05

状态：方案设计

## 1. 项目概述

本项目要建设一个台风实况信息网站，让公众在几秒内看懂当前台风的关键动态。首屏必须回答以下五个问题：

| 用户问题 | 展示字段 | 示例形式 |
| --- | --- | --- |
| 台风叫什么？ | 中文名、英文名、台风编号 | “中文名 / 英文名 / 第 N 号台风” |
| 台风在哪里？ | 经纬度、相对区域或海区 | “某海区，北纬 N°、东经 E°” |
| 台风往哪里走？ | 移动方向、移动速度 | “向指定方向移动，时速 N 公里” |
| 台风是什么等级？ | 当前强度等级 | “数据源发布的等级” |
| 风力有多大？ | 最大风速、风力等级 | “最大风速 N 米/秒，阵风 N 级” |

除这五项之外，网站还应始终显示数据来源和最后更新时间，避免用户把旧数据当成实时状态。

## 2. 产品目标与原则

### 2.1 产品目标

- 用户进入首页后无需跳转，即可找到台风名称、位置、移动方向、等级和风力。
- 在手机和桌面端都能快速阅读，弱网环境下也能尽快看到核心文字信息。
- 每条实况数据都能追溯到明确来源和更新时间。
- 对“暂无数据、数据延迟、接口错误”等情况给出诚实清晰的提示。

### 2.2 设计原则

1. **信息优先**：台风名称与当前强度先于装饰性地图和品牌内容。
2. **可验证**：来源、发布时间、更新时间与更新时间状态必须可见。
3. **少猜测**：无法从数据源确认的信息显示“暂未发布”，不根据模型自行补写。
4. **不只靠颜色**：等级和警示同时使用文字、图标、数值与颜色。
5. **移动端优先**：小屏首屏先显示五项核心信息，地图可随页面继续向下浏览。
6. **克制提醒**：不使用“最危险”“一定登陆”等未经权威信息支持的绝对化表达。

## 3. MVP 范围

### 3.1 本期包含

- 单页面台风实况首页。
- 当前活跃台风卡片；有多个台风时支持切换。
- 五项核心实况信息。
- 台风当前位置与最近移动轨迹地图。
- 最近若干次定位的路径点。
- 数据来源、发布时间、抓取/生成时间和是否延迟的提示。
- 手动刷新与自动刷新。
- 加载、空状态、接口失败和过期数据状态。
- 手机、平板、桌面响应式布局。
- 基础无障碍和搜索引擎优化。

### 3.2 本期暂不包含

- 用户账号、收藏和历史订阅。
- 多国预报路径对比与概率圈分析。
- 灾害损失统计、新闻聚合和社区讨论。
- 本地化预警推送。
- 原生 App。
- 自动生成登陆结论或避险决策。

## 4. 信息架构与页面设计

### 4.1 首页结构

1. **顶部状态栏**
   - 项目名称。
   - “数据更新于 HH:mm”状态。
   - 手动刷新按钮。

2. **台风实况主卡**
   - 台风中文名、英文名和编号。
   - 当前等级标签。
   - 位置、移动方向、移动速度和最大风速。
   - 数据来源与发布时间。
   - 有多个活跃台风时，用简洁选择器切换。

3. **台风路径地图**
   - 当前中心点使用醒目标记。
   - 已发生路径按时间顺序连线，并标明关键节点时间。
   - 点击定位点可查看该时次位置、等级和风速。
   - 提供地图图层开关和缩放控件。

4. **强度概览**
   - 最大风速、阵风、中心气压（数据源提供时）。
   - 风圈半径（数据源提供时）。
   - 用数值和文字双重表达强度。

5. **来源与安全提示**
   - 数据源名称、官方链接、发布时间。
   - “实况信息可能更新，预警与防灾请以当地气象部门发布为准”的固定提示。

### 4.2 首屏优先级

移动端首屏顺序建议为：

1. 台风名称
2. 当前等级
3. 位置
4. 移动方向与速度
5. 最大风速
6. 更新时间与来源

地图排在这些文字信息之后，避免用户为了找关键答案而拖拽地图。

### 4.3 视觉方向

- 深蓝到青色的海洋背景，白色主文字，层级清楚。
- 台风等级使用有区分度的暖色警示，但颜色不作为唯一标识。
- 数据数字使用等宽或清晰数字字体，单位与数值保持接近。
- 卡片边界、留白和分割线保持克制，整体像“专业气象仪表盘”，不像娱乐资讯站。
- 动效只用于刷新、状态切换和路径点淡入，并尊重“减少动态效果”系统设置。

## 5. 数据策略

### 5.1 数据字段

建议统一为以下内部数据结构：

```ts
type TyphoonSnapshot = {
  id: string;
  number?: string;
  nameZh: string;
  nameEn?: string;
  position: {
    latitude: number;
    longitude: number;
    areaLabel?: string;
    observedAt: string;
  };
  movement: {
    directionLabel: string;
    directionDegrees?: number;
    speedKph?: number;
  };
  intensity: {
    grade: string;
    maxWindMs?: number;
    gustLevel?: number | string;
    minPressureHpa?: number;
  };
  source: {
    name: string;
    url: string;
    publishedAt: string;
    fetchedAt: string;
  };
  track: Array<{
    latitude: number;
    longitude: number;
    observedAt: string;
    grade?: string;
    maxWindMs?: number;
  }>;
  isStale: boolean;
};
```

字段为空时显示“数据源未提供”，不显示 `0`、`undefined` 或自行推算结果。

所有时间字段使用带时区的 ISO 8601 字符串存储，例如 `2026-11-05T12:00:00+08:00`；界面按用户时区格式化，并明确显示观察时区。

### 5.2 数据源选择

正式开发前必须确认数据源及使用条款，优先顺序为：

1. 官方公开接口或官方授权数据。
2. 有明确授权、稳定 SLA 和再分发许可的商业数据服务。
3. 在许可范围内做的缓存快照；必须标注来源和原始时间。

候选来源可包括中国气象局、香港天文台等机构发布的信息，但只有在接口、授权和稳定性确认后才能作为生产来源。

不将未经许可的网页抓取作为正式方案。若官方仅提供页面而无可稳定接入的数据接口，需在开工前决定：使用授权数据服务、维持人工半自动更新，或调整 MVP 的“自动实时”范围。

### 5.3 更新与缓存

- 建议服务端每 5 至 10 分钟检查一次数据；具体频率服从数据源要求和更新节奏。
- 所有用户共用服务端缓存，避免直接对上游发起高频请求。
- 上游数据未变化时，保留上次有效快照。
- 页面显示两类时间：数据源发布时间和本站最后检查/获取时间。
- 超过预设有效期（建议为 30 分钟，按来源调整）时显示“数据可能已延迟”。
- 上游失败时优先展示上次有效数据，并明确标出过期状态；没有有效数据时显示错误说明和官方来源链接。

### 5.4 数据质量规则

- 经纬度必须在合法范围内，并确认坐标顺序。
- 风速、气压与等级的单位必须统一；不同来源的 10 分钟平均风和 1 分钟平均风不得混用而不说明。
- 同一台风同一观测时次不得重复展示。
- 强度等级以数据源原值为准；网站改变颜色不改写等级。
- 移动方向既展示文字，也可逐步补充方位角，便于绘制路径。
- 所有对外展示的数据都保留 `source` 与 `observedAt`。

## 6. 技术方案

### 6.1 推荐技术栈

- 框架：Next.js + TypeScript
- 样式：Tailwind CSS
- 地图：MapLibre GL JS
- 图表：优先使用轻量的原生 SVG；复杂趋势图再引入图表库
- 数据接入：Next.js Route Handler 作为服务端适配与代理层
- 缓存：先使用服务端内存/HTTP 缓存，部署环境明确后可接入 Redis
- 测试：Vitest + Testing Library，关键流程使用 Playwright
- 部署：选择可支持定时任务、服务端缓存和日志的平台

### 6.2 架构

```text
官方或授权数据源
        |
        v
服务端数据适配层
  - 拉取、鉴权、字段映射
  - 单位统一、质量校验
  - 缓存、限流、失败回退
        |
        v
Next.js 页面与只读 API
        |
        +--> 实况卡
        +--> 路径地图
        +--> 数据来源与更新时间
```

数据适配层必须与页面组件解耦。以后更换数据源时，页面不需要重做。

### 6.3 建议目录

```text
app/
  page.tsx
  api/typhoons/current/route.ts
components/
  typhoon-summary.tsx
  typhoon-map.tsx
  data-status.tsx
  source-note.tsx
lib/
  data/
    provider.ts
    normalize.ts
    cache.ts
  format.ts
types/
  typhoon.ts
fixtures/
  sample-typhoon.ts
docs/
  PLAN.md
```

## 7. 交互与异常状态

- 页面打开时先使用缓存数据渲染，随后在后台检查更新。
- 手动刷新期间按钮显示进行中状态；不阻塞已有个性化阅读位置。
- 切换台风时，保留当前地图位置，但给出明确的选中状态。
- 鼠标悬停与触摸点击都支持读取路径点详情。
- 数据延迟时使用高对比度文字提示，并提供官方来源链接。
- 接口失败时不循环弹窗；只在数据状态区域说明问题。
- 地图加载失败时仍展示五项文字信息、经纬度和来源。
- 无活跃台风时显示“当前暂无活跃台风”，并标注数据时间。

## 8. 无障碍与响应式要求

- 正文对比度至少达到 WCAG AA。
- 关键信息在 360 px 宽度下无需横向滚动。
- 地图支持键盘操作，并提供路径点的文字替代视图。
- 所有图标有可理解的文本或 `aria-label`。
- 单位、数字和方向标签对屏幕阅读器可连贯朗读。
- 刷新、延迟和错误状态通过可读文本传达。
- 动画遵守 `prefers-reduced-motion`。

## 9. 性能与安全

- 首屏核心信息在常规 4G 网络下目标 2.5 秒内可读。
- 地图脚本按需加载，不阻塞实况文字。
- 上游密钥只保存在服务端环境变量中。
- API 返回做字段白名单处理，不直接透传不可信内容。
- 对上游请求设置超时、有限重试和退避策略。
- 生产环境启用 CSP、HTTPS、合理的缓存头和访问日志。
- 地图底图、字体和图标必须确认授权及署名要求。

## 10. 开发阶段与交付物

### 阶段 0：数据与合规确认

- 确认首发地域、正式数据源及授权。
- 获取接口文档、字段定义、频率限制和示例响应。
- 确认地图底图与公开部署合规性。

交付物：数据源结论、示例响应、字段映射草案。

### 阶段 1：产品原型与视觉方向

- 完成移动端和桌面端低保真结构。
- 完成一项高保真首页方案。
- 用模拟数据覆盖加载、正常、延迟、空状态和错误状态。

交付物：可浏览原型、视觉规范、模拟数据。

### 阶段 2：前端 MVP

- 搭建项目骨架和响应式页面。
- 完成实况卡、路径地图、来源说明和状态组件。
- 完成格式化、错误边界与基础无障碍。

交付物：可本地运行、可通过模拟数据验收的网站。

### 阶段 3：真实数据接入

- 实现数据源适配、字段标准化、缓存和失败回退。
- 加入自动检查与手动刷新。
- 验证坐标、单位、时间时区及多台风切换。

交付物：连接正式数据源的预发布版本。

### 阶段 4：测试、部署与上线

- 完成单元、集成和端到端测试。
- 进行真实手机、弱网和异常数据演练。
- 部署、配置监控并记录回滚步骤。

交付物：生产网站、运行手册和首版验收记录。

## 11. 测试与验收

### 11.1 必测场景

- 单个活跃台风。
- 多个活跃台风。
- 无活跃台风。
- 数据字段缺失。
- 没有经纬度。
- 上游接口超时和返回格式变化。
- 缓存数据已过期。
- 地图瓦片或地图脚本加载失败。
- 手机横竖屏、桌面宽屏和 200% 缩放。
- 键盘与屏幕阅读器核心流程。

### 11.2 MVP 验收标准

- 首页无需展开“更多信息”即可看到名称、位置、移动方向、等级和最大风速。
- 每项核心信息都有单位或明确文字语义。
- 用户能一眼找到数据来源、数据发布时间和本站最后更新时间。
- 有多个台风时能够明确切换，且不会混淆名称和路径。
- 上游失败时页面仍可访问，并区分“旧数据”和“无数据”。
- 360 px 宽度下没有横向溢出，关键信息不被地图遮挡。
- 所有主要状态不依赖颜色表达。
- 关键路径点可点击，也有等价的文字路径列表。
- 不展示未经数据源确认的登陆地点、登陆时间或灾害结论。

## 12. 主要风险与处理

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 官方数据接口不稳定或未公开 | 无法按时实现自动实时 | 阶段 0 先确认；准备授权服务、人工半自动更新或缩小范围 |
| 不同来源风力定义不同 | 等级与风速被误读 | 统一内部字段和单位，明确统计口径 |
| 上游数据延迟 | 用户误判为当前实况 | 始终显示发布时间、抓取时间和延迟提示 |
| 地图服务或底图授权不清晰 | 无法公开部署 | 选用条款明确的底图并保留署名 |
| 多台风和路径点过多 | 移动端难读 | 默认突出当前选中台风，图例可开关，提供文字列表 |
| 特殊时期访问量激增 | 上游或站点过载 | 服务端缓存、限流、静态化非动态部分并准备降级页面 |

## 13. 开工前待确认

1. 网站首发地区及主要语言。
2. 正式数据源、接口授权、调用频率和再分发条件。
3. 是否展示预测路径，还是只展示已经发生的实况路径。
4. 品牌名称、Logo、域名和部署位置。
5. 是否需要多台风同时对比。
6. 是否需要接入当地预警信号或应急避险入口。
7. 地图底图与公开服务的合规要求。
